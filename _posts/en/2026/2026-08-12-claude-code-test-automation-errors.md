## Problem: Why Claude Code Generated Tests Break in Production

Automatically generated test code often works fine initially, but in live service, the following symptoms appear:

- Integration exceptions due to inconsistent mock object configurations
- QA environment breakage due to unexpected side effects
- Conflicts from duplicated tests in every commit
- Delayed debugging due to test function names/descriptions differing from actual functionality

These issues are particularly critical because "failures are discovered too late." Local execution results might look good, but the system behaves strangely in staging/production, or issues are only caught in the CI pipeline.

## Principle: Claude Code's Suggestion Method and Blind Spots

Claude Code proposes new tests by reading code descriptions or existing test code and identifying patterns. With well-crafted natural language prompts, it can quickly generate repetitive, templated code.

However, in these situations:
- It often fails to adequately consider internal function dependencies or business rule contexts (especially for database/external API mocking).
- If the context (input code scope) is not properly defined, it may suggest incomplete mock objects, test doubles, or fixtures.
- When multiple people use Claude Code, the machine-suggested fixture names, test function names, and scenario descriptions can diverge across teams and PRs, cluttering the codebase.

## Real Code/Setup: Reproducing Failure Scenarios

Below is an example of a Python test automatically generated by Claude Code. It appears normal and passes in pytest.

```python
# Claude Code가 제안한 목 객체 사용 예시
import pytest
from app.user import get_user_profile

class DummyUser:
    def __init__(self, name):
        self.name = name

def test_user_profile_returns_name():
    dummy = DummyUser("alice")
    assert get_user_profile(dummy) == "alice profile"
```

While the actual service function references internal components like DB connections or external caches, Claude Code ignores this context and only suggests a dummy test that "passes if the name matches."

Problems arise when dependencies like the following are added to the actual code:

```python
# 실서비스에서 변경된 함수 (DB 연결 등)
def get_user_profile(user):
    user_data = db.fetch_user(user.name)  # 목 객체에서 누락
    return f"{user_data['name']} profile"
```

It passes in CI, but a DB connection exception occurs in staging.

## Caveats: Checklist for Applying Claude Code Test Automation

- Clearly specify external dependencies (database, cache, API) for the function under test.
- Explicitly state the actual behavior of mock objects (e.g., `fetch_user` return value) in code comments or prompts.
- Always manually review Claude Code's suggested test code and verify that fixtures/doubles are synchronized with actual service changes.
- When multiple people use Claude Code simultaneously, standardize fixture modules, function names, and test description templates as a convention beforehand.

## Conclusion: Pay Attention to These Situations When Automating Tests with Claude Code

| Situation                          | Recommendation                        | Reason                                                                                                 |
|------------------------------------|---------------------------------------|--------------------------------------------------------------------------------------------------------|
| Solo development, side projects    | Recommended (manual verification essential) | Lower difficulty in understanding/modifying code context; automation brings significant benefits       |
| Startups with under 5 people       | Partial use                           | Requires template/convention guidelines and a regular review system                                    |
| Legacy code, multiple team members | Limited adoption                      | Complex dependencies and extensive concurrent work lead to significant side effects. Requires custom checklists and parallel test design |
