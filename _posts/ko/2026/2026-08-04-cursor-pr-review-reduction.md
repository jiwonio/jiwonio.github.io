금요일 오후, 50개 파일이 변경된 Pull Request(PR)가 올라왔습니다. 기능 구현에 꼭 필요한 대규모 리팩토링이 포함되어 변경 사항이 많습니다. 동료들은 '월요일에 볼게요'라는 코멘트만 남기고, 결국 다음 주 배포 일정은 기약 없이 밀리기 시작합니다. 리뷰어는 어디서부터 봐야 할지 막막하고, PR 작성자는 리뷰가 늦어지면서 생기는 충돌(conflict)을 해결하느라 시간을 허비합니다.

이런 상황의 근본 원인은 컨텍스트 부족입니다. 리뷰어는 변경된 코드의 전체 맥락을 파악하는 데 상당한 인지 자원을 소모해야 합니다. 모든 함수 호출 관계를 추적하고, 사이드 이펙트 가능성을 따져보는 과정은 지루하고 어렵습니다. 결국 리뷰는 피상적인 코드 스타일에만 집중되거나, 핵심 로직은 제대로 보지 못한 채 'LGTM'을 남기게 될 수도 있습니다.

### Before: 컨텍스트를 찾아 헤매는 수동 리뷰

기존의 코드 리뷰 방식은 대부분 다음과 같은 과정을 거칩니다.

1.  **브랜치 체크아웃:** 리뷰할 PR의 브랜치를 로컬 환경으로 가져옵니다. 최신 상태가 아니면 베이스 브랜치와 병합하는 과정이 추가됩니다.
2.  **변경점 파악:** IDE에서 변경된 파일 목록을 하나씩 열어봅니다. 파일이 많으면 어떤 파일부터 봐야 할지 우선순위를 정하기 어렵습니다.
3.  **영향도 분석:** 특정 함수의 변경이 어떤 부분에 영향을 미치는지 파악하기 위해 수동으로 모든 호출부를 찾아다닙니다. IDE의 'Find Usages' 기능에 의존하지만, 동적으로 호출되는 부분이나 인터페이스 뒤에 숨은 구현체는 놓치기 쉽습니다.
4.  **질문과 답변:** 이해가 안 되는 부분은 PR 코멘트로 질문을 남깁니다. 작성자의 답변을 기다리는 시간 동안 리뷰는 중단됩니다. 답변이 달려도 원래 보던 맥락을 다시 기억해내는 데 시간이 걸립니다.

이 과정의 가장 큰 문제는 모든 부담이 리뷰어 개인의 경험과 기억력에 의존한다는 점입니다. 특히 복잡한 레거시 시스템이나 여러 도메인이 얽힌 코드베이스라면 한 명의 개발자가 모든 컨텍스트를 파악하기는 거의 불가능에 가깝습니다.

### After: AI와 함께하는 컨텍스트 기반 리뷰

Cursor는 코드베이스 전체를 이해하는 AI와의 대화 기능을 제공합니다. 이를 활용하면 리뷰 워크플로가 극적으로 바뀝니다. 이제 PR 작성자와 리뷰어의 입장에서 각각 어떻게 활용할 수 있는지 살펴보겠습니다.

#### PR 작성자의 준비 과정

리뷰 요청 전에 작성자는 Cursor를 이용해 리뷰어가 궁금해할 만한 내용을 미리 정리할 수 있습니다. 이는 리뷰의 질을 높이고 시간을 단축하는 중요한 단계입니다.

`@Codebase` 심볼을 이용해 프로젝트 전체 파일을 대상으로 질문을 던집니다.

```
@Codebase 이 PR의 주요 변경 사항을 비즈니스 관점에서 요약해줘.
그리고 잠재적인 사이드 이펙트가 발생할 수 있는 부분을 3가지 정도 알려줘.
```

AI는 이 질문에 답하기 위해 변경된 파일들의 연관 관계를 분석하고, 핵심 로직의 변화를 요약해 줍니다. 이렇게 생성된 요약문을 PR 설명(description)에 추가하면, 리뷰어는 코드를 보기 전에 전체적인 그림을 먼저 이해할 수 있습니다.

#### 리뷰어의 탐색 과정

리뷰어는 더 이상 모든 코드를 한 줄씩 읽을 필요가 없습니다. 대신 AI에게 질문하며 핵심을 빠르게 파고들 수 있습니다.

로컬에 브랜치를 받아 Cursor로 연 뒤, 궁금한 함수나 클래스를 선택하고 AI 채팅창에 질문합니다.

```
이 함수의 변경으로 인해 영향을 받는 API 엔드포인트는 어디야?
```

또는 특정 로직이 복잡하게 느껴진다면, 설명을 요청할 수 있습니다.

```
이 정규표현식이 정확히 어떤 패턴을 검증하는지 한국어로 설명해줘.
```

이 방식은 수동으로 코드를 추적하는 것보다 훨씬 빠르고 정확합니다. 리뷰어는 피상적인 부분 대신, 실제 비즈니스 로직의 타당성이나 엣지 케이스 처리 여부 등 더 중요한 문제에 집중할 수 있게 됩니다. 질문과 답변이 비동기적인 코멘트가 아닌, 실시간 대화처럼 이루어지므로 리뷰가 막힘없이 진행됩니다.

### 주의할 점

물론 AI의 답변이 항상 완벽하지는 않습니다. 때로는 최신 변경 사항을 잘못 해석하거나 미묘한 비즈니스 맥락을 놓칠 수 있습니다. 따라서 AI가 생성한 요약이나 분석은 리뷰를 돕는 '초안'으로 생각하고, 최종 판단은 반드시 리뷰어 본인이 내려야 합니다.

AI는 코드의 '구문적' 의미와 구조적 관계는 잘 파악하지만, 이 코드가 왜 '그렇게' 작성되어야만 했는지와 같은 '의도'는 파악하기 어렵습니다. 따라서 "이 로직이 우리 회사의 X 정책을 준수하나요?" 같은 질문보다는 "이 함수의 시간 복잡도는 얼마인가요?" 와 같이 코드 자체에 기반한 질문을 할 때 더 좋은 답변을 얻을 수 있습니다.
