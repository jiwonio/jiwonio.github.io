## 문제 정의: 파편화된 컨텍스트

레거시 코드 분석이 어려운 근본적인 이유는 코드의 맥락이 여러 파일에 걸쳐 파편화되어 있기 때문입니다. 예를 들어, 사용자의 결제 요청을 처리하는 로직은 다음과 같이 흩어져 있을 수 있습니다.

*   `controllers/payment_controller.rb`: HTTP 요청을 받아 서비스 호출
*   `services/payment_service.rb`: 비즈니스 로직 처리, 여러 모델과 상호작용
*   `models/order.rb`: 주문 상태 관리
*   `models/user.rb`: 사용자 정보 조회
*   `lib/external_api_client.rb`: 외부 결제 PG사 API 연동

이런 상황에서 `payment_service.rb` 파일만 LLM에 입력하고 "이 코드의 문제점을 찾아줘"라고 질문하면, 모델은 `Order`나 `User` 모델의 내부 구현이나 `ExternalAPIClient`의 인터페이스를 전혀 알지 못하므로 절반의 정보로 추측성 답변만 내놓게 됩니다.

기존 모델의 컨텍스트 창(예: 32K, 128K 토큰)은 이런 규모의 코드를 한 번에 담기에 턱없이 부족했습니다. 이것이 우리가 겪는 문제의 핵심입니다.

## Gemini 1.5 Pro의 긴 컨텍스트는 어떻게 다른가

Gemini 1.5 Pro는 최대 100만 토큰의 컨텍스트 창을 지원합니다. 이는 일반적인 소설책 몇 권 분량에 해당하며, 웬만한 중소 규모의 서비스나 모듈 전체 소스 코드를 한 번에 입력할 수 있는 크기입니다.

컨텍스트 창이 크다는 것은 단순히 더 많은 텍스트를 입력할 수 있다는 의미를 넘어섭니다. 모델이 코드베이스의 모든 파일을 동시에 "읽고" 파일 간의 상호 참조, 데이터 흐름, 숨겨진 의존성을 종합적으로 파악할 수 있게 됩니다. 즉, 파편화된 컨텍스트 문제를 정면으로 해결할 수 있는 기반이 마련된 것입니다.

### 1. 분석 대상 코드 취합하기

먼저 분석하려는 모듈과 관련된 모든 소스 코드 파일을 하나의 텍스트 파일로 합치는 작업이 필요합니다. 수십 개의 파일을 일일이 복사하여 붙여넣는 것은 비효율적이므로 간단한 쉘 스크립트를 활용하는 것이 좋습니다.

```bash
# 분석할 디렉터리로 이동
cd path/to/legacy/project

# 1. 파일 구조를 먼저 파악하고,
# 2. 관련 있는 파일들을 하나의 텍스트 파일로 합칩니다.
echo "Project structure:" > combined_code.txt
tree . -I 'tmp|log|vendor' >> combined_code.txt
echo "\n--- End of structure ---\n" >> combined_code.txt

# Ruby on Rails 프로젝트의 app 디렉터리 전체를 합치는 예시
# 프로젝트에 맞게 `find` 명령어의 경로와 확장자를 수정해야 합니다.
find app -name "*.rb" -print0 | while IFS= read -r -d $'\0' file; do
    echo "--- File: $file ---" >> combined_code.txt
    cat "$file" >> combined_code.txt
    echo "\n" >> combined_code.txt
done
```

이 스크립트는 먼저 `tree` 명령어로 전체 파일 구조를 텍스트 파일 상단에 기록하여 모델이 코드의 위치를 파악하는 데 도움을 줍니다. 그 후 `find` 명령어로 특정 확장자를 가진 모든 파일을 찾아 `combined_code.txt` 파일에 순차적으로 추가합니다.

잘 취합된 코드만큼이나 중요한 것이 바로 프롬프트입니다. 모델에게 명확한 역할과 목표, 출력 형식을 지정해주어야 원하는 분석 결과를 얻을 수 있습니다.

다음은 레거시 코드 분석을 위한 프롬프트 예시입니다.

```text
당신은 20년 경력의 Ruby on Rails 백엔드 아키텍트입니다. 저는 유지보수를 위해 오래된 결제 모듈을 분석해야 합니다. 아래에 `combined_code.txt` 파일의 전체 내용이 제공됩니다.

이 코드베이스 전체를 깊이 있게 분석한 후, 다음 질문에 대해 상세히 답변해 주십시오.

[분석 목표]
1.  사용자가 API를 통해 결제를 요청했을 때, `controllers/payment_controller.rb`의 `create` 액션부터 시작하여 외부 PG사 API 호출까지 이어지는 전체 코드 실행 흐름을 순서대로 설명해 주십시오. 각 단계에서 어떤 파일의 어떤 클래스, 어떤 메서드가 호출되는지 명시해야 합니다.
2.  `PaymentService` 클래스의 가장 핵심적인 책임(responsibility)은 무엇입_니까?
3.  이 코드베이스에서 잠재적인 버그나 심각한 성능 저하를 유발할 수 있는 부분을 3가지 찾아내고, 그 이유와 함께 개선 방안을 제시해 주십시오. 예를 들어, N+1 쿼리 문제, 부적절한 예외 처리, 하드코딩된 설정 값 등을 찾아주세요.
4.  이 결제 모듈의 데이터베이스 스키마를 Mermaid JS의 ERD 다이어그램 형식으로 그려주세요.

답변은 한국어로, 각 항목을 마크다운으로 명확히 구분하여 작성해 주십시오.

--- BEGINNING OF CODEBASE ---
(여기에 위에서 생성한 combined_code.txt 파일의 내용을 모두 붙여넣습니다)
```

이 프롬프트는 다음과 같은 핵심 요소를 포함합니다.

*   **명확한 컨텍스트 제공**: 코드베이스 전체를 제공한다는 사실을 명시합니다.
*   **구체적인 질문**: 단순한 분석 요청이 아닌, 실행 흐름, 클래스 책임, 잠재적 문제점, 데이터베이스 스키마 시각화 등 구체적이고 실행 가능한(actionable) 결과물을 요구합니다.

## 주의할 점: 토큰 비용과 한계

긴 컨텍스트 창은 강력하지만 만능은 아닙니다. 실제 업무에 적용하기 전 몇 가지 고려할 점이 있습니다.

*   **API 비용**: 100만 토큰을 입력으로 사용하는 것은 상당한 비용이 발생할 수 있습니다. 매번 사소한 질문을 할 때마다 전체 코드를 입력하기보다는, 큰 그림을 파악하거나 복잡한 리팩터링 계획을 세우는 등 중요한 분석에 간헐적으로 사용하는 것이 합리적입니다.
*   **"大海 속 바늘 찾기(Needle in a Haystack)" 문제**: 컨텍스트가 매우 길어지면 모델이 그 안의 특정 정보를 놓치는 경우가 발생할 수 있다는 연구 결과가 있습니다. 중요한 분석을 수행할 때는 프롬프트를 통해 모델의 주의를 특정 파일이나 로직으로 유도하거나, 답변을 비판적으로 검토하는 과정이 반드시 필요합니다.
*   **응답 지연 시간**: 입력 크기가 큰 만큼 응답을 받기까지 수십 초에서 몇 분까지 소요될 수 있습니다. 실시간 대화보다는 비동기적인 분석 작업에 더 적합합니다.
