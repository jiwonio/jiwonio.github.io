## 問題の定義：断片化されたコンテキスト

レガシーコード分析が困難である根本的な理由は、コードのコンテキストが複数のファイルにまたがって断片化されているためです。例えば、ユーザーの決済リクエストを処理するロジックは、次のように分散している可能性があります。

*   `controllers/payment_controller.rb`: HTTPリクエストを受け付け、サービスを呼び出す
*   `services/payment_service.rb`: ビジネスロジックを処理し、複数のモデルと相互作用する
*   `models/order.rb`: 注文状態を管理する
*   `models/user.rb`: ユーザー情報を参照する
*   `lib/external_api_client.rb`: 外部決済PG社APIと連携する

このような状況で、`payment_service.rb`ファイルだけをLLMに入力して「このコードの問題点を見つけてください」と質問しても、モデルは`Order`や`User`モデルの内部実装や`ExternalAPIClient`のインターフェースを全く知らないため、半分の情報で推測に基づいた回答しかできません。

従来のモデルのコンテキストウィンドウ（例：32K、128Kトークン）では、この規模のコードを一度に収めるには全く不十分でした。これが私たちが直面する問題の核心です。

## Gemini 1.5 Proの長文コンテキストはどう違うのか

Gemini 1.5 Proは最大100万トークンのコンテキストウィンドウをサポートしています。これは一般的な小説数冊分に相当し、ほとんどの中小規模のサービスやモジュール全体のソースコードを一度に入力できるサイズです。

コンテキストウィンドウが大きいということは、単に多くのテキストを入力できるという意味を超えます。モデルがコードベースのすべてのファイルを同時に「読み」、ファイル間の相互参照、データフロー、隠れた依存関係を総合的に把握できるようになります。つまり、断片化されたコンテキストの問題を正面から解決できる基盤が整ったのです。

## 実際のワークフロー：コードベースの統合とプロンプト設計

次に、レガシーコードベースをGemini 1.5 Proに効果的に入力し、分析を依頼する具体的な手順を見ていきましょう。

### 1. 分析対象コードの統合

まず、分析したいモジュールに関連するすべてのソースコードファイルを一つのテキストファイルにまとめる作業が必要です。数十個のファイルを一つずつコピー＆ペーストするのは非効率的なため、簡単なシェルスクリプトを活用することをお勧めします。

```bash
# 分析するディレクトリに移動
cd path/to/legacy/project

# 1. ファイル構造を先に把握し、
# 2. 関連するファイルを一つのテキストファイルに統合します。
echo "Project structure:" > combined_code.txt
tree . -I 'tmp|log|vendor' >> combined_code.txt
echo "\n--- End of structure ---\n" >> combined_code.txt

# Ruby on Railsプロジェクトのappディレクトリ全体を統合する例
# プロジェクトに合わせて`find`コマンドのパスと拡張子を修正する必要があります。
find app -name "*.rb" -print0 | while IFS= read -r -d $'\0' file; do
    echo "--- File: $file ---" >> combined_code.txt
    cat "$file" >> combined_code.txt
    echo "\n" >> combined_code.txt
done
```

このスクリプトは、まず`tree`コマンドで全体のファイル構造をテキストファイルの上部に記録し、モデルがコードの位置を把握するのに役立てます。その後、`find`コマンドで特定の拡張子を持つすべてのファイルを見つけ、`combined_code.txt`ファイルに順次追加します。

### 2. プロンプトの設計

適切に統合されたコードと同様に重要なのがプロンプトです。モデルに明確な役割、目標、出力形式を指定することで、望む分析結果を得ることができます。

以下に、レガシーコード分析のためのプロンプト例を示します。

```text
あなたは20年以上の経験を持つRuby on Railsのバックエンドアーキテクトです。私は保守のために古い決済モジュールを分析する必要があります。以下に`combined_code.txt`ファイルの全内容を提供します。

このコードベース全体を深く分析した後、次の質問について詳細に回答してください。

[分析目標]
1.  ユーザーがAPIを通じて決済をリクエストした際、`controllers/payment_controller.rb`の`create`アクションから始まり、外部PG社API呼び出しに至るまでの全体コード実行フローを順序立てて説明してください。各段階でどのファイルのどのクラス、どのメソッドが呼び出されるかを明記する必要があります。
2.  `PaymentService`クラスの最も核となる責任(responsibility)は何ですか？
3.  このコードベースにおいて、潜在的なバグや深刻なパフォーマンス低下を引き起こす可能性のある箇所を3つ特定し、その理由とともに改善策を提案してください。例えば、N+1クエリ問題、不適切な例外処理、ハードコーディングされた設定値などを見つけてください。
4.  この決済モジュールのデータベーススキーマをMermaid JSのERDダイアグラム形式で描画してください。

回答は日本語で、各項目をマークダウンで明確に区切って作成してください。

--- BEGINNING OF CODEBASE ---
(ここに上で生成した combined_code.txt ファイルの内容をすべて貼り付けます)
--- END OF CODEBASE ---
```

このプロンプトは、以下の重要な要素を含んでいます。

*   **ペルソナ付与**: 「20年以上の経験を持つバックエンドアーキテクト」という役割を与えることで、専門的な観点から分析するよう促します。
*   **明確なコンテキストの提供**: コードベース全体を提供することを明示します。
*   **具体的な質問**: 単純な分析依頼ではなく、実行フロー、クラスの責任、潜在的な問題点、データベーススキーマの視覚化など、具体的で実行可能な(actionable)成果物を要求します。

## 注意点：トークンコストと限界

長文コンテキストウィンドウは強力ですが、万能ではありません。実際の業務に適用する前に、いくつかの考慮点があります。

*   **APIコスト**: 100万トークンを入力として使用することは、かなりのコストが発生する可能性があります。些細な質問をするたびに全体コードを入力するよりも、全体像を把握したり、複雑なリファクタリング計画を立てるなど、重要な分析に断続的に使用するのが合理的です。
*   **「干し草の山から針を見つける(Needle in a Haystack)」問題**: コンテキストが非常に長くなると、モデルがその中の特定の情報を見落とす場合があるという研究結果があります。重要な分析を行う際は、プロンプトを通じてモデルの注意を特定のファイルやロジックに誘導するか、回答を批判的に検討する過程が必須です。
*   **応答遅延時間**: 入力サイズが大きいほど、応答を受け取るまでに数十秒から数分かかることがあります。リアルタイムの対話よりも、非同期的な分析作業に適しています。
